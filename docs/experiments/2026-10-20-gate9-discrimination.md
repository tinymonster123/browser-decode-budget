# 2026-10-20 — Gate 9：小 matmul 和大 matmul，哪个缺口是真的

## 判据（先于结果）

1. 至少 **90%** 的 MatMulNBits 时间和 **90%** 的回放 dispatch 必须对上已知权重指纹；
   否则本 gate 判为负结果，不猜。
2. workgroup 数必须出现在 **95%** 以上的已归因 segment 上；否则「并行度」这个问题
   没有答案。
3. 每个档位报 split→batched。若 split 把某档位抬高 **>15%**，Gate 7/8 的该档位
   绝对值要修正，报告使用修正值。
4. 只有某个候选的**修正后上界 ≥10% token 时间**、且杠杆在栈内时，才进入优化 gate。

这四条写在 `bench/browser/gate9-discrimination.mjs` 里，运行前已固定。

## 问题

Gate 8 按「每次 dispatch 读的权重字节数」分层，得到两个候选：

- **A. 小 matmul 并行度受限**：0.22 MiB 档 10.7–15.2 GB/s，远低于大档位；
- **B. 大 matmul 内存效率不足**：档位 ≥3.47 MiB 只有 55.9–72.7 GB/s。

但 Gate 7/8 的测量方式是**一 dispatch 一 pass**。它给每个 dispatch 加了一个 pass
边界，并且去掉了共享 pass 里可能的重叠。Gate 9 只回答两个问题：

1. 这个测量模式把绝对值抬高了多少？
2. 小 matmul 的缺口是并行度、固定成本，还是档位划分本身有问题？

## 方法

### 1. workgroup 数

`splitPass` 记录每次 `dispatchWorkgroups(x,y,z)` 的参数；shader module 创建时从
WGSL 源码里读 `workgroup_size_x/y/z`（ORT 把三个值声明成 u32 常量，再传给
`@workgroup_size`，所以解析的是常量值）。两者相乘得到 invocation 数。这是运行时
唯一能看到的「形状」信号。

### 2. 同一 dispatch 的两种编码

归因跑完后，页面保留每个 dispatch 的真实 `pipeline`、bind group 和 dispatch 参数。
对每类选一个代表，把**同一个 dispatch** 在同一个 device 上重放 N 次：

- **batched**：N 次 dispatch 放进一个 pass；
- **split**：N 个 pass，每 pass 一次 dispatch，带 timestamp。

重复同一个 dispatch 会让它的输出 buffer 出现写后写依赖，WebGPU 的次序保证会
把它们串行化，所以 batched 不会因为意外的并行而变快。权重在重复之间留在缓存里，
这让结果**偏袒**小 kernel（如果连热权重都慢，缓存就不是解释）。

### 3. 合成尺寸扫描（E3）并入重放

原计划的 E3 是「用合成 buffer 扫 0.2/1.7/10/20 MiB」。实际数据里，
workgroup=192 这一族覆盖 0.22 / 1.73 / 3.47 / 5.20 / 10.41 MiB 五个真实形状；
整体档位还包括 20.81 MiB，所以 **0.2–20 MiB 的尺寸范围由真实档位覆盖**，
「不经过 ORT 调度」这一点由重放（自己的 encoder）提供。再加一组合成 buffer
不会增加判别力，所以本 gate 用真实 kernel 扫描，并在报告里明确这是方法上的替换。

### 档位划分的修正

运行时按 **(权重指纹的字节多重集, workgroup 数)** 分组，而不是只按字节。原因见
结果第一张表。

## 结果

### 1. 同一个字节数不是同一个 kernel

`runs/2026-10-20-exp7-weight-bytes-by-op.json` 的指纹只按字节分组。把 ONNX 图里
每个 MatMulNBits 节点的权重 dims 枚举出来后，同一个字节档位里有多种形状：

| 指纹字节 | 图上形状（节点数） | 运行时 workgroup |
|---:|---|---:|
| 227,328 | `[256,48,16]` × 59（k/v/input_gate） + `[1536,8,16]` × 35（per-layer projection） | 32 vs 192 |
| 1,818,624 | `[2048,48,16]` × 28（q_proj） + `[1536,64,16]` × 28（o_proj） | 256 vs 192 |
| 3,637,248 | `[4096,48,16]` × 7（q_proj） + `[1536,128,16]` × 7（o_proj） | 512 vs 192 |
| 10,911,744 | `[12288,48,16]` × 15（gate_up） + `[1536,384,16]` × 20（down_proj） | 1536 vs 192 |

所以 Gate 8 的「0.22 MiB k_proj 档」是一个混合体：59 个 N=256 的 kernel 和
35 个 N=1536 的 kernel。Gate 8 报的 10.7–15.2 GB/s 是两者的平均值。**这是 Gate 8
结论需要修正的地方**，不是 Gate 9 新加的猜测：分组来自图上的 dims，
workgroup 数来自运行时，两侧独立。

下面的表全部按 `(字节, workgroup)` 分组。

**结论：** 在缓存能容纳的档位（≤0.43 MiB）上，split 比 batched 每次 dispatch
多 **约 1 µs（1.0–1.3 µs）**；两次运行一致。大档位的 Δ 是 −330…+30 µs 的噪声，
因为重放让权重留在缓存里，split 与 batched 的缓存状态不同——这些 Δ **不是**
pass 边界成本，不能当修正系数用。

因此判据 3 的判定是：split 模式的成本约 **1 µs/dispatch**。对小 kernel 的冷时间
（12.4–22.5 µs）是 **4–11%**，低于 15% 阈值；Gate 8 的绝对值只需要减去约 1 µs，
不需要按比例打折。

注意不能把热权重的比例直接套到冷时间上：k_proj 的热权重 split/batched 是
6.7/5.6 µs（+20%），但分母是热权重下的 5.6 µs；冷时间的分母是 12–23 µs，
同一个 1 µs 只占 4–11%。判据 3 用的是**冷绝对值**，所以没有触发 >15% 的修正。

### 4. 固定成本：192-workgroup 家族的尺寸扫描

workgroup=192 的四个真实形状（同一 kernel 家族，只改权重字节数），用冷数据
做线性拟合（推论，不是实测）：

| 权重 MiB | 冷 µs A | 冷 µs B |
|---:|---:|---:|
| 0.22 | 15.1 | 20.7 |
| 1.73 | 30.7 | 33.1 |
| 3.47 | 55.6 | 55.9 |
| 5.20 | 86.0 | 82.3 |
| 10.41 | 141.7 | 152.4 |
| **拟合** | **固定 12.4 µs + 82.6 GB/s** | **固定 13.1 µs + 79.1 GB/s** |

线性拟合 **R² = 0.9922 / 0.9961**（由 L1/L2 的 192-wg 点重算）：固定成本 +
边际带宽解释了 **>99%** 的尺寸趋势。交接文档的「E1+E3 解释 ≥80%」判据通过。

即：每次 dispatch 有一笔 **12.4–13.1 µs 的固定成本**（两轮拟合），之后才按
约 **79–85 GB/s** 的边际带宽读权重。截距对最小的两个点最敏感（0.22 MiB 的冷
时间是 12–21 µs），所以只应读量级，不应读小数位；稳定的是边际带宽。

这给出了候选 A 的量级（推论）：小档位共 **156 次 dispatch/step**
（59+28+28+35+6），固定成本全部消失最多省
**156 × 12.4–13.1 µs = 1.93–2.04 ms = 7.1–7.5% token**。这条上限没有达到 10%。

| A（敏感性：同轮最好档位） | 3.26 / 4.24 ms | 86.9 / 77.0 GB/s | 1.45 / 1.64 ms | 1.82 / 2.61 ms | 6.7% / 9.6% |
| B. 大档位（≥2 MiB） | 15.50 / 17.11 ms | **同轮最好档位** 86.9 / 77.0 GB/s | 13.71 / 15.48 ms | 1.79 / 1.63 ms | **6.6% / 6.0%** |
| B（敏感性） | 15.50 / 17.11 ms | Gate 5 的 86.18 GB/s（loadavg 2.24） | 13.83 ms | 1.67 / 3.28 ms | 6.1% / **12.0%** |

A 的主行用同轮大档位的**中位带宽**（保守），敏感性行用**同轮最好档位**；
两种参照都低于 10%。B 的主行用同轮最好档位。

参照带宽用的是**未扣 pass 成本的冷数据**，而候选时间是扣过 1 µs 的。若参照也
扣同样的 1 µs，它的带宽会高约 1%，headroom 会再小约 0.05 ms——所以表里的
headroom 是保守上界，不是下界。

**B 的主判据是对预注册参照（Gate 5 的 86.18）的事后修正**：86.18 是在
loadavg 2.24 下测的，而 B 轮的 loadavg 是 4.70；跨负载比较
绝对 GB/s 正是同一份交接文档禁止的做法。原始参照的结果仍保留在表里：B 轮用
86.18 得到 12.0%，但同一轮里最好的大档位只有 77.0 GB/s——这个 12% 里有一部分
是负载差，不是 kernel 效率差。同轮口径下 A、B 都低于 10%。

split/batched >15% 的档位：A 轮只有 0.22 MiB/32 wg（1.21x）；B 轮有
0.22 MiB/32 wg（1.23x）、10.41 MiB/1536 wg（1.17x）、3.47 MiB/192 wg（1.79x）。
这些比值的分母是**热权重**时间，而且 3.47 MiB/192 wg 的 hot split 明显异常
（37.1 vs 冷 55.9 µs），所以不套到冷时间上；判据 3 用冷绝对值判定。

最后一行不构成候选：**没有任何实测 matmul kernel 达到 109 GB/s**，最好的是
run A 的 86.9 GB/s（L1），Gate 6 的 109 是纯读 kernel。

## 交叉检查

- **覆盖率**：两次运行都是 100% 的 MatMulNBits 时间对上指纹，0 unmatched、
  0 ambiguous；100% 的已归因 segment 带 workgroup 数；回放覆盖 100% 的 dispatch，
  0 个 indirect dispatch；决策表 **242/242** 次 dispatch 都 join 上了回放档位。
  判据 1、2 通过。
- **两次一致性**：13 个档位里 7 个的冷 µs 差 ≤8%，1 个 8.9%，5 个 >10%
  （10.5–44.8%）；两个最小档位差 **44.8% / 26.7%**，3.47 MiB/512 wg
  档差 42.3%。差异方向与负载一致
  （B 轮 loadavg 4.70 更高、整体慢 14%），但最小档位仍不可靠。
  **结论不依赖这些点估计**：两次的 headroom 都 <10%（A 5.4%/8.8%，B 6.6%/6.0%）。
- **回放是否忠实**：split 回放的每 dispatch 时间与同一轮冷归因对得上
  （例如 10.41 MiB/192 wg：24.5 vs 141.7——差在缓存；0.22 MiB/32 wg：
  6.7 vs 12.4——同样是缓存）。**回放是热权重测量，只能用来比较两种编码，
  不能当冷绝对值。** 报告里的冷数字全部来自归因列，不来自回放。
- **uniform 写**：4 步共 4,448 次 `queue.writeBuffer`，对应全部 op 的
  1,112 dispatch/step × 4（MatMulNBits 是 242/step），但只有 **43 个不同 buffer**。所以 uniform buffer 按 program/形状共享，不是
  每节点一个。重放前把每个代表档位绑定的、≤4 KiB 的 buffer 按最后一次写入
  恢复（13 次），形状在 decode 中是静态的，所以内容一致。
- **workgroup 不等于并行度结论**：同样 192 workgroups、24,576 invocations，
  0.22 MiB 档是 11–15 GB/s，10.41 MiB 档是 72–77 GB/s。并行度不是唯一变量；
  **每次 dispatch 的字节数**（也就是固定成本能不能摊薄）才是主轴。
- **和 Gate 8 对撞**：Gate 8 的 0.22 MiB 档 10.7–15.2 GB/s 是混合档位；
  拆开后 k_proj 是 **10.1–18.3 GB/s**，per-layer projection 是
  **11.0–15.0 GB/s**。Gate 8 的排序（带宽随字节下降）仍成立，但「小档位」
  的绝对值需要按新分组读。
- **和 Gate 7 对撞**：Gate 7 的 17.76–18.10 ms（loadavg 2.72–3.48）落在
  Gate 9 的 19.02 ms（2.96）和 21.64 ms（4.70）之间，方向与负载一致。
- **负载**：A 轮 2.96 / B 轮 4.70；Gate 8 是 5.04/5.90。跨负载的绝对值差
  约 14–20%（matmul 19.0 → 21.6 ms），与 loadavg 方向一致。

## 结论

**两个候选都没有达到 10% 的门槛；本 gate 判为负结果，不进入优化 gate。**

实测到的事实：

1. **同一个权重字节数不是同一个 kernel。** Gate 8 的档位混合了不同形状
   （0.22 MiB = 59 个 `[256,48,16]` + 35 个 `[1536,8,16]`）。按
   `(字节, workgroup)` 拆分后，k_proj 和 per-layer projection 的效率不同。
2. **split 模式的成本约 1 µs/dispatch**（直接测得，两次一致），相当于
   最小 kernel 冷时间的 4–11%，低于 15% 的修正阈值。Gate 7/8 的绝对值不需要
   按比例打折；扣掉约 1 µs 即可。
3. **每次 dispatch 有 12.4–13.1 µs 的固定成本**（两轮拟合范围，推论）。
   0.22 MiB 的 dispatch 只读 227 KB，固定成本占一半以上，所以有效带宽低。
   这不是简单的「workgroup 太少」：同样 192 workgroups，0.22 MiB 只有
   11–15 GB/s，10.41 MiB 有 72–77 GB/s。
4. **候选 A 的上界是 7.1–7.5%**：156 次小 dispatch/step × 固定成本。
   按「达到同轮大档位中位带宽」算是 5.4%/8.8%；最激进的口径
   （同轮最好档位）是 6.7%/9.6%，仍低于 10%。
5. **候选 B 的上界是 6.0–6.6%**：同轮最好的大档位是 77.0–86.9 GB/s，
   大档位整体离它只有几个百分点。用跨负载的 86.18 会让 B 轮算出 12.0%，
   但那不是同条件可兑现的 kernel 杠杆。
6. 唯一能稳定过 10% 的数字是「达到纯读上限 109.06 GB/s」（16.8–22.7%），
   但没有任何 matmul kernel 测到过它；兑现它需要一个比现有最好 kernel
   再快 20–25% 的内核，这不在本仓库的范围内。

即使数值过线，两个候选的杠杆都是自定义/合并 kernel，属于仓库的非目标，
所以判据 4 的「杠杆在栈内」也不通过。

**这条性能线的下一步不是继续找 kernel 微优化，而是承认：在 q4f16 + ORT WebGPU
的现有实现下，decode 的 27.2 ms 里能靠「改图 / 改调度 / 改小 matmul 形状」
拿到的部分已经接近耗尽。** 剩下的两个大数字——固定成本约 1.9–2.0 ms、大档位
距同轮最好档位约 1.6–1.8 ms——都低于 10%，且都要求换 kernel 或换运行时，
属于新项目级别的决定，不是当前仓库的 gate 能回答的。

## 未回答

1. **12.4–13.1 µs 固定成本的来源**：没有拆成 launch、workgroup 调度、尾部 drain、
   内存延迟。只知道它随 dispatch 存在，且不随 workgroup 数线性变化；
   截距本身对最小档位敏感。
2. **最小档位的运行间波动**：k_proj 两次是 12.4 / 22.5 µs（−45%），per-layer
   projection 是 15.1 / 20.7 µs（−27%）。需要更多重复才能给出可信区间；
   本 gate 只用它们做上界，不用它们做点估计。
3. **长上下文**：KV cache 和 attention 占比会变，本轮是短 prompt。
4. **如果把多个小 matmul 合并成一个 dispatch**：本 gate 没有实现，也没有估计
   合并后的 kernel 成本；只知道「删掉固定成本」的上界是 7.1–7.5%。
5. **Gate 8 的 0.43 MiB 档**（6 次 dispatch）：样本太小，两次差 8.9%，
   没有单独下结论。
